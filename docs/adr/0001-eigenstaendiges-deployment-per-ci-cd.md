# Eigenständiges Deployment per CI/CD, ohne Ansible-Abhängigkeit

Schwarmstack wird als Container-Image gebaut und per CI/CD deployt (Staging und Produktion). Das Repo enthält alles, was es zum Einrichten des Hosts, Bauen und Deployen braucht; es hängt nicht von `home-ansible` oder einem anderen privaten Repo ab. `home-ansible` spielt auch bei der Einrichtung des Hosts keine Rolle: Projekt und private Infrastruktur bleiben vollständig getrennt. Die erste Fassung ging davon aus, dass eine Ansible-Rolle in einem Nachbar-Repo das Release holt und installiert; das koppelte Projekt und Betrieb unnötig.

- Zwei Umgebungen: **Produktion** unter `upload.example.com` und **Staging** unter `staging.example.com`, je ein eigener Server und ein eigener Bucket im Hetzner-Konto des Betreibers. Staging hat keinerlei Verbindung zu DZVF; für die Produktion setzt DZVF nur den DNS-Eintrag. Lokale Entwicklung läuft ohne Server, mit lokaler Platte.
- Server und Hetzner-Firewall (22/80/443) werden von Hand in der Hetzner Console angelegt, nicht als Code. Eingerichtet wird ein frischer Ubuntu-26.04-Server per cloud-init aus dem Repo; dasselbe Skript lässt sich als Fallback per SSH ausführen. Es installiert Docker aus dem offiziellen Repo, legt einen Benutzer `deploy` (Gruppe `docker`, nur Schlüssel-Login) an und schaltet automatische Sicherheitsupdates ein.
- Beide laufen mit Docker Compose aus demselben Image: App (gunicorn, statische Dateien über WhiteNoise) und Caddy (TLS). Staging ist zusätzlich per Basic Auth in Caddy geschützt. SQLite liegt auf der lokalen Platte des Servers.
- GitHub Actions baut das Image nach GHCR, getaggt mit `sha-<commit>` (Package `schwarmstack-ci`) bzw. `vX.Y.Z` (Release, Package `schwarmstack`, ADR 0011), nie `latest`. Die getrennten Packages halten die Versionsliste des Release-Images frei von den vielen `sha-`-Ständen. Jeder Push auf `main` geht per Deploy nach Staging; nach Produktion geht ein Image `vX.Y.Z` nur bewusst per „Run workflow“, mit manueller Freigabe (ADR 0011: Der Tag selbst deployt nichts). Der Deploy läuft per SSH: `.env` aus den GitHub-Environment-Secrets schreiben, mit dem kurzlebigen Job-Token bei GHCR anmelden und das Image ziehen, Migrationen als eigener Schritt (schlagen sie fehl, läuft die alte Version weiter), dann `docker compose up -d` und Warten auf `/healthz` (Ablauf in `docs/betrieb/deployment.md`). Ein Rollback ist ein erneuter Deploy eines älteren Tags. Ein Deploy unterbricht die Seite für wenige Sekunden; Uploads der Master laufen direkt zu S3 und sind nicht betroffen.

## Considered Options

- **Ansible-Rolle in `home-ansible`, Release als Tarball** (erster Ansatz): verworfen wegen der Kopplung an ein privates Repo und weil Staging dann nur über den Betreiber testbar war.
- **Grundeinrichtung des Hosts über `home-ansible`**: verworfen, um Projekt und private Infrastruktur nicht zu vermischen.
- **Server und Firewall als Code (`hcloud`, OpenTofu)**: verworfen, für eine einmalige Aktion mit zwei Servern zu viel Aufwand.
- **Dauerhafter GHCR-Token auf dem Host oder öffentliches Image**: verworfen; das kurzlebige Job-Token lässt kein Geheimnis auf dem Server zurück, und das Repo bleibt privat.
- **Deploy ohne Unterbrechung (zwei App-Container)**: verworfen, weil die kurze Unterbrechung nur Seitenaufrufe trifft, nicht die Uploads.
